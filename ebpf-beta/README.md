# CloudWatch Agent eBPF beta

Branch `exp/ebpf-mode` (plan C) = CloudWatch Agent v1.300074.0 (go.mod unchanged) + the OBI
eBPF process as its own binary, `amazon-cloudwatch-agent-ebpf`, built from `third_party/obi` (a
separate Go module). One RPM, one tarball, one image; the eBPF process is the only one with
capabilities and pushes OTLP/gRPC to the agent over a Unix socket. Buildable from this branch alone:

| Path | What |
|---|---|
| `third_party/obi/` | OpenTelemetry eBPF Instrumentation v0.12.2 + adot-obi patches (source only; see `ADOT_OBI_SOURCE`); its `cmd/obi` is the eBPF binary |
| `packaging/dependencies/amazon-cloudwatch-agent-ebpf.{yaml,service}` | the eBPF process's config (`ebpf/obi.yaml`, root-owned) and its systemd unit |
| `packaging/dependencies/amazon-cloudwatch-agent-ebpf-receiver.yaml` | the agent's eBPF receiving pipeline (`etc/ebpf/receiver.yaml`) |
| `ebpf-beta/ci/` | `run.sh` (all checks), dependency-version gate and its v1.300074.0 baselines |
| `ebpf-beta/e2e/` | runtime test with restricted capabilities |
| `ebpf-beta/binary/` | standalone tarball: the RPM's files + `install.sh` / `uninstall.sh` (no rpm needed) |
| `ebpf-beta/containers/` | the image (built by the user from the tarball), EKS DaemonSet and ECS task: two containers each; see its README |
| `ebpf-beta/configtest/` | `etc/ebpf/receiver.yaml` must validate with the agent's components |
| `ebpf-beta/obiconfigtest/` | `ebpf/obi.yaml` must load with OBI's loader (own module, like the binary) |
| `.github/workflows/ebpf-beta.yml` | CI: gates, e2e, RPM; manual release |

`third_party/obi` is generated by adot-obi's `scripts/vendor-into-cwagent.sh`: change OBI in
adot-obi, re-run it, commit the result here (and drop the `receiver/obireceiver` copy it writes:
the agent no longer compiles OBI in).

## Build

Needs Linux, Go and docker. OBI's BPF bindings are not committed: `make ebpf-generate` builds
them in OBI's pinned generator image, and the Linux build targets run it first.

```
ebpf-beta/ci/run.sh              # gates (= deps unit cross) + e2e (e2e needs sudo)
ebpf-beta/ci/run.sh rpm          # RPMs + tarballs in build/ebpf-beta/bin/linux/{amd64,arm64}/
VERSION=1.300074.0-ebpfbeta.1 ebpf-beta/ci/run.sh rpm
```

## Standalone tarball

`amazon-cloudwatch-agent.tar.gz` (built from each RPM by `ebpf-beta/binary/build-tarball.sh`)
installs the same files, `cwagent` user and systemd units without rpm:

```
tar -xzf amazon-cloudwatch-agent-<version>.linux-amd64.tar.gz && cd amazon-cloudwatch-agent-ebpf-beta
sudo ./install.sh                                   # install or upgrade; keeps edited configs
sudo amazon-cloudwatch-agent-ctl -a enable-ebpf     # eBPF on: starts amazon-cloudwatch-agent-ebpf.service
sudo ./uninstall.sh
```

The capabilities come only from `amazon-cloudwatch-agent-ebpf.service` (user cwagent, ambient
capabilities), as with the RPM; the agent itself runs with none. Do not grant them with `setcap`
(every user who can run the file would get them) or run the eBPF binary as root.

## Image

`ebpf-beta/ci/run.sh image` builds `ebpf-beta/containers/Dockerfile` from the release tarballs
(as users build it; linux/amd64 into the local docker, smoke-tested); CI pushes linux/amd64 +
linux/arm64 to `ghcr.io/<owner>/cloudwatch-agent-ebpf-beta`. See `ebpf-beta/containers/README.md`
for EKS and ECS: two containers from the same image, the agent and the eBPF process.

## Release

Actions > ebpf-beta > Run workflow, with `release` set (e.g. `1.300074.0-ebpfbeta.1`): runs all
checks, pushes the image tag `<release>`, then creates the GitHub pre-release `v<release>` with both RPMs. Do not push `v*` tags by
hand: they start upstream workflows that need CloudWatch Agent team AWS roles. Publishing to SSM
Distributor is manual (adot-obi `distributor/publish.sh`).
