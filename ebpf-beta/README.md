# CloudWatch Agent eBPF beta

Branch `ebpf-beta` = CloudWatch Agent v1.300074.0 + the OBI eBPF receiver, buildable from
this branch alone:

| Path | What |
|---|---|
| `third_party/obi/` | OpenTelemetry eBPF Instrumentation v0.12.2 + adot-obi patches (source only; see `ADOT_OBI_SOURCE`) |
| `receiver/obireceiver/` | the `obi` receiver, registered in `service/defaultcomponents` |
| `packaging/dependencies/amazon-cloudwatch-agent-ebpf.{yaml,conf}` | RPM default eBPF config (`etc/ebpf/obi.yaml`) and systemd drop-in |
| `ebpf-beta/ci/` | `run.sh` (all checks), dependency-version gate and its v1.300074.0 baselines |
| `ebpf-beta/e2e/` | runtime test with restricted capabilities |
| `ebpf-beta/binary/` | standalone tarball: the RPM's files + `install.sh` / `uninstall.sh` (no rpm needed) |
| `ebpf-beta/image/Dockerfile` | official CloudWatch Agent image layout + `etc/ebpf/obi.yaml` |
| `ebpf-beta/containers/` | EKS DaemonSet and ECS DAEMON task for that image (no add-on); see its README |
| `ebpf-beta/configtest/` | the RPM eBPF config must validate with the agent's components |
| `.github/workflows/ebpf-beta.yml` | CI: gates, e2e, RPM; manual release |

`third_party/obi` and `receiver/obireceiver` are generated by adot-obi's
`scripts/vendor-into-cwagent.sh`: change OBI in adot-obi, re-run it, commit the result here.

## Build

Needs Linux, Go and docker. OBI's BPF bindings are not committed: `make ebpf-generate` builds
them in OBI's pinned generator image, and the Linux build targets run it first.

```
ebpf-beta/ci/run.sh              # gates (= deps unit cross) + e2e (e2e needs sudo)
ebpf-beta/ci/run.sh rpm          # RPMs + tarballs in build/ebpf-beta/bin/linux/{amd64,arm64}/
VERSION=1.300074.0-ebpfbeta.1 ebpf-beta/ci/run.sh rpm
```

## Standalone tarball

`amazon-cloudwatch-agent.tar.gz` (built from each RPM by `ebpf-beta/binary/build-tarball.sh`)
installs the same files, `cwagent` user and systemd units without rpm:

```
tar -xzf amazon-cloudwatch-agent-<version>.linux-amd64.tar.gz && cd amazon-cloudwatch-agent-ebpf-beta
sudo ./install.sh                                   # install or upgrade; keeps edited configs
sudo amazon-cloudwatch-agent-ctl -a enable-ebpf     # eBPF on: cwagent + the capabilities via systemd
sudo ./uninstall.sh
```

The capabilities come only from the systemd drop-in, as with the RPM. Do not grant them with
`setcap` (every user who can run the file would get them) or run the agent as root.

## Capabilities and Java agent injection

`enable-ebpf` runs the agent as the unprivileged `cwagent` user and grants, through the systemd
drop-in, only the capabilities of the features `etc/ebpf/obi.yaml` enables:

| Feature (setting in `obi.yaml`) | Default | Capabilities |
|---|---|---|
| RED metrics | always | `CAP_BPF CAP_PERFMON CAP_SYS_PTRACE CAP_DAC_READ_SEARCH CAP_CHECKPOINT_RESTORE CAP_NET_RAW` |
| Topology, `peer.service.name` (`ebpf.context_propagation`) | `tcp_service_name` | `+ CAP_NET_ADMIN CAP_SYS_ADMIN` |
| Java agent injection (`javaagent.enabled`) | `true` | `+ CAP_SYS_ADMIN CAP_KILL CAP_SYS_CHROOT CAP_SETUID CAP_SETGID` |
| Node.js injection (`nodejs.enabled`) | `false` | `+ CAP_KILL` |

After changing these settings, run `sudo amazon-cloudwatch-agent-ctl -a enable-ebpf` again: it
rewrites the drop-in with the matching capabilities and restarts the agent.

**Java agent injection loads an agent into your JVMs.** For HTTPS in Java (JSSE does not use
OpenSSL, so eBPF cannot see the plaintext), the agent copies a small Java agent jar into the
JVM's own `/tmp` (or `/var/tmp`) and loads it through the JVM attach API, into every JVM it
instruments, also JVMs owned by other users or root, and JVMs in containers. The attach runs on
one dedicated thread of the agent, which switches to the JVM owner's uid/gid only for the attach.
To turn it off (Java HTTPS is then not measured; plain HTTP still is), set
`javaagent: {enabled: false}` under `receivers: obi/cwagent_ebpf:` and run `enable-ebpf` again:
`CAP_SETUID`, `CAP_SETGID`, `CAP_SYS_CHROOT` and `CAP_KILL` are then no longer granted.

## Metric cardinality

Some metric attributes come from request data: on HTTP server metrics, `peer.service.name` is the
`X-Forwarded-Host` (else `Host`) the client sent (the name the service was called by, which joins
the topology through load balancers); on HTTP client metrics, `server.address` and the AWS
resource attributes (`aws.s3.bucket`, `aws.sqs.queue.url`, `aws.lambda.function.arn`). A value
that is not a plausible host name / AWS resource is dropped, and per service only the first 50
`peer.service.name` values (100 per AWS attribute) are kept; further values are reported as
`_other`. In addition, the drop-in sets `OTEL_GO_X_CARDINALITY_LIMIT=2000`: at most 2000
attribute sets per service and metric, the rest aggregated into one series with
`otel.metric.overflow=true`.

## Image

`ebpf-beta/ci/run.sh image` builds the image (linux/amd64 into the local docker, smoke-tested);
CI pushes linux/amd64 + linux/arm64 to `ghcr.io/<owner>/cloudwatch-agent-ebpf-beta` as `<sha7>`,
`latest` (branch `ebpf-beta`) and `<release>`. Same layout and entrypoint as the official
`amazon/cloudwatch-agent` image, so it can replace it (EKS add-on / operator). eBPF is off, as in
the RPM, until `/opt/aws/amazon-cloudwatch-agent/etc/ebpf/enabled` exists (mount an empty file);
the container then needs the eBPF capabilities (or `privileged`), host PID and the host's
`/sys/fs/cgroup` mounted at `/sys/fs/cgroup` (in the container's own cgroup namespace OBI
would attach its sockops program to the container's cgroup only: RED works, `peer.service.name` does not).

## Release

Actions > ebpf-beta > Run workflow, with `release` set (e.g. `1.300074.0-ebpfbeta.1`): runs all
checks, pushes the image tag `<release>`, then creates the GitHub pre-release `v<release>` with both RPMs. Do not push `v*` tags by
hand: they start upstream workflows that need CloudWatch Agent team AWS roles. Publishing to SSM
Distributor is manual (adot-obi `distributor/publish.sh`).
